# CQA — оценка качества диалогов

Проект команды **Bibigon**.

Рабочее приложение для Freedom Broker Data Challenge: React + TypeScript + Vite,
FastAPI + Python, SQLite и LLM через OpenAI-совместимый API, включая OpenRouter.

## Что уже работает

- Чек-лист из восьми критериев с весами, разрешёнными ступенями шкал и условиями N/A.
- Сохранение новых версий чек-листа через API. Существующая версия неизменяема.
- Импорт JSON организаторов и отдельных транскриптов RU/KZ/EN.
- Вставка обычной переписки: модель определяет участников, исходный текст восстанавливается из строк без переписывания. Роли можно исправить; неоднозначные фрагменты требуют проверки. Отсутствующее время не придумывается.
- Плеер записи: перемотка, переходы по таймкодам, скорость, отключение звука и повторная загрузка после ошибки.
- Сохранение исходных ролей, текста, порядка и меток времени. ID реплик `m0001`, `m0002` и т. д.
- Один запрос к настроенной модели с полным диалогом и текущим чек-листом.
- JSON Schema для поддерживающих его моделей; JSON mode для DeepSeek с той же обязательной локальной проверкой структуры, покрытия критериев, допустимых оценок и доказательств.
- Детерминированный расчёт итогового балла и результатов секций.
- Сохранение входных данных, оценок, хешей, версии промпта, модели, токенов и стоимости, если провайдер её возвращает.
- STT через Scribe v2 в OpenRouter: исходное аудио, таймкоды, разделение говорящих и явное назначение ролей перед оценкой.
- Независимая проверка каждого критерия через Jev: дискретные ответы и список расхождений без автоматического изменения оценки.
- Интерфейс в фирменном стиле Freedom: поиск, фильтры, загрузка JSON/аудио, история оценок, очередь спорных результатов, аудиоплеер и переходы от оценки к исходным репликам.
- Экспорт списка в CSV и подробной оценки в JSON. Технические метаданные и расходы доступны через API, но не показываются в пользовательских экранах.
- Редактор чек-листа: критерии, веса, шкалы, условия N/A и версии без изменения старых оценок.
- Фильтр грубых ошибок в последних AI-оценках; апелляции по конкретной оценке и критерию.
- Рассмотрение апелляции, история действий и отдельные результаты QA с пересчётом через общий движок.

Числовая оценка не генерируется при отсутствии ключа или ошибке модели.
Фиктивный провайдер существует только в тестах. Тестовые решения не являются Ground Truth.

## Структура

```text
backend/
  src/cqa/
    rubrics/freedom-chat-v1.json  # начальный чек-лист
    models.py                   # контракты входа, критериев и результата
    inputs.py                   # нормализация, загрузка чек-листа, хеши
    engine.py                   # валидация доказательств и расчёт
    prompt.py                   # инструкция оценщику и схема ответа
    provider.py                 # адаптер LLM / OpenRouter
    audio.py                    # ограниченная загрузка и проверка аудио
    transcription.py            # Scribe, таймкоды, подтверждение ролей
    text_import.py              # автоматическое определение ролей в вставленном тексте
    decisions.py                # независимые дискретные решения Jev
    operations.py               # сохранение результатов и журнал вызовов
    extensions.py               # STT, decision checks, расходы: HTTP API
    pilot.py                    # малый возобновляемый платный эксперимент
    service.py                  # запуск оценки и метаданные
    storage.py                  # неизменяемые записи в SQLite
    api.py                      # FastAPI factory
    settings.py                 # локальная конфигурация
    cli.py                      # импорт DEV без обращения к модели
  tests/
  pyproject.toml
  requirements.lock.txt
frontend/
  src/                         # React-каркас и клиент API
  package-lock.json
.env.example                   # конфигурация без ключей
data/                          # локальная SQLite, исключена из Git
tmp/                           # скачанный DEV и временные данные, исключены из Git
```

## Запуск на Windows / PowerShell

Нужны Python 3.12+ и Node.js 22.12+ (проверено на Python 3.14 и Node.js 25).
Все команды ниже выполняются из корня проекта, если не указано иное.

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r backend/requirements.lock.txt
.\.venv\Scripts\python.exe -m pip install -e ./backend --no-deps
```

Если `.env` ещё не создан:

```powershell
Copy-Item .env.example .env
```

Для OpenRouter в `.env` задайте:

```dotenv
LLM_BASE_URL=https://openrouter.ai/api/v1
LLM_API_KEY=your-key
LLM_MODEL=deepseek/deepseek-v4.1-flash-1017
LLM_TIMEOUT_SECONDS=150
LLM_MAX_OUTPUT_TOKENS=12000
STT_MODEL=elevenlabs/scribe-v2
DECISION_MODEL=typesafe/jev-1.14
CQA_DB_PATH=data/cqa.sqlite3
```

DeepSeek 1017 использует `json_object`, схему в инструкции и `reasoning.effort=low`.
Предпочтительные маршруты — Fireworks/Together; настройки приватности аккаунта
не изменяются. Полученный JSON всегда проверяется локально до расчёта и сохранения.
Другие модели используют строгий `json_schema`. Маршрутизация OpenRouter использует
`provider.require_parameters=true`. Адаптер не выполняет автоматические повторы и не переключает
модель при ошибке. Лимит выходных токенов ограничивает длину ответа, но не задаёт общий
денежный бюджет. `cost_usd=null` означает, что стоимость не сообщена, а не нулевую цену.

Ключ хранится только на backend. `.env`, локальные данные и базы исключены из Git.
Не помещайте секреты в переменные `VITE_*`.

Перед первым запуском задайте пароль рабочего пространства:

```powershell
.\.venv\Scripts\python.exe -m cqa.admin
```

В `.env` записывается только scrypt-хеш. Для генерации случайного пароля используйте
`--generate`: пароль сохраняется в `.secrets/admin-password.txt` (исключён из Git).
После смены пароля перезапустите backend: старые сессии перестанут работать.

Запуск backend:

```powershell
.\.venv\Scripts\python.exe -m uvicorn cqa.api:create_app --factory --reload --host 127.0.0.1 --port 8000
```

Во втором терминале:

```powershell
cd frontend
npm.cmd ci
npm.cmd run dev
```

- Интерфейс: http://127.0.0.1:5173
- Публичная проверка доступности: http://127.0.0.1:8000/healthz
- Подробное состояние после входа: http://127.0.0.1:8000/api/health

Vite проксирует `/api` на backend; Swagger и OpenAPI отключены. Для локальной
разработки оба процесса слушают loopback. Для интернета используйте собранный frontend
и HTTPS через Caddy: [инструкция развёртывания](deploy/README.md).

Схема запросов: браузер → наш backend → OpenRouter. Браузер не получает ключ
провайдера. Все диалоги, оценки, аудио и платные операции требуют серверной сессии.
Описание защиты и её границ — в [SECURITY.md](SECURITY.md).

## Импорт DEV и запуск оценки

Если сохранён ответ API организаторов:

```powershell
.\.venv\Scripts\python.exe -m cqa.cli 'tmp/dev-dataset.json'
```

Импорт проверяет весь пакет до записи и не вызывает LLM. Повторный импорт того же
содержимого не создаёт дубликаты. Изменённый транскрипт с прежним `conversation_id`
сохраняется как отдельный снимок с другим хешем.

В интерфейсе загрузите диалог и нажмите «Оценить». Соответствующие HTTP-операции
для собственного клиента (требуют cookie-сессии; POST также требует разрешённый
Origin, `X-CQA-Request: 1` и `X-CSRF-Token` из `/api/auth/session`):

1. `POST /api/conversations/import` — вставить JSON ответа организаторов; или
   `POST /api/conversations` — передать один объект записи.
2. `GET /api/conversations` — получить `hash` нужного диалога.
3. `GET /api/checklists` — получить `hash` версии чек-листа.
4. `POST /api/evaluations` — передать `conversation_hash` и `checklist_hash`.
   **Этот endpoint отправляет диалог настроенному провайдеру и может расходовать кредиты.**
5. `GET /api/evaluations/{id}` — прочитать сохранённый результат.

Чтобы применить новый критерий, измените конфигурацию, увеличьте `version`, сохраните
её через `POST /api/checklists` и передайте новый хеш в следующий запуск оценки.
Типы критериев: `binary`, `scale`, `flag`. У `flag` вес всегда 0. Сумма весов не обязана
равняться 100: результат нормализуется по применимым весам.

## Аудио и независимая проверка

1. Откройте звонок, выберите вкладку «Аудио» и нажмите «Расшифровать аудио».
   Свой файл можно загрузить кнопкой «Загрузить диалоги»; сохранённые расшифровки доступны в разделе «Аудио».
2. Откройте расшифровку, прослушайте фрагменты и назначьте каждому говорящему
   роль оператора, клиента или автоответчика. Затем подтвердите роли и язык.
3. Создаётся отдельный диалог с происхождением от STT; его можно оценить тем же движком.
   Исходный транскрипт организаторов остаётся отдельным снимком.
4. Откройте «Перепроверка» в карточке оценки. Независимый проверяющий получает исходный диалог и чек-лист,
   но не ответы основного оценщика. Его ответы не заменяют итог автоматически.

STT и Jev используют OpenRouter и `LLM_API_KEY`. Для загрузок разрешены MP3, WAV,
FLAC, MP4 и Ogg, до 25 MiB и 15 минут. Удалённые ссылки принимаются только с двух
настроенных доменов организаторов; перенаправления проверяются повторно. Неопределённые
говорящие блокируют создание оцениваемого диалога. Расшифровка сама по себе не гарантирует
точного распознавания речи или правильного разделения голосов.

Дополнительные endpoints: `GET /api/transcriptions`, `GET /api/transcriptions/{id}`,
`GET /api/transcriptions/{id}/audio`, `POST /api/transcriptions/{id}/conversation`,
`GET /api/evaluations`, `POST /api/decision-checks`, `GET /api/decision-checks`,
`GET /api/usage`. Журнал отмечает начатые, успешные и ошибочные вызовы.
Расходы суммируются только по полученным данным провайдера; неизвестная стоимость
и возможное списание за неуспешный запрос не считаются бесплатными.

Малый платный эксперимент (одна запись и три чата RU/KZ/EN):

```powershell
.\.venv\Scripts\python.exe -m cqa.pilot --run
```

Результаты находятся в `tmp/pilot/report.json`. Повторный запуск использует уже
сохранённые в отчёте успешные шаги. При аварии между записью результата и обновлением
отчёта сначала проверьте журнал: автоматической гарантии однократного списания нет.
Этот прогон проверяет интеграцию, а не точность относительно Ground Truth.

## Чек-листы, апелляции и ручная проверка

В разделе «Чек-лист» выберите версию и нажмите «Редактировать чек-лист».
Измените правила, вес или добавьте критерий. Сохранение создаёт новую версию.
В карточке диалога выберите её и запустите оценку; старый результат остаётся в истории.
Изменение веса не запускает внешнюю модель автоматически.

В списке диалогов фильтр «Грубые ошибки AI» показывает флаги именно последних
AI-оценок, отдельно от общего списка «На проверку». В карточке откройте критерий,
чтобы увидеть объяснение и исходные реплики.

Для апелляции выберите нужную оценку в истории, вкладку «Апелляции», критерий,
имя и причину. В разделе «Апелляции» открываются обращения по той же версии оценки.
QA берёт обращение на рассмотрение, принимает или отклоняет с обоснованием.
При принятии нужно выбрать ответ и подтверждающие реплики. N/A требует отдельного
основания. Снимки QA накапливают принятые изменения; исходный AI-результат неизменяем.
Переключатель «Источник оценки» показывает исходный результат или последний результат QA.
Экспорт подробной оценки включает оба результата, если есть решение QA.

Имена вводятся вручную в общем доверенном рабочем пространстве. Это не отдельные
аккаунты и не разграничение доступа оператор/QA. История хранится на сервере;
повторное закрытие и две открытые апелляции по одному критерию одной оценки запрещены.

## Сравнение с ручной разметкой

Команды не вызывают внешние модели. Создайте пустой шаблон:

```powershell
.\.venv\Scripts\python.exe -m cqa.benchmark template --output tmp/manual-labels.json
```

Независимо разметьте решения `yes/no/na/score_0.5` по чек-листу. `score_...` должен
соответствовать разрешённой ступени. Укажите `family` для группы похожих сценариев,
`split` (`calibration` или `holdout`), затем `reviewed: true`. `total_score` необязателен:
он нужен для сравнения итогового балла. Оставляйте неподтверждённые записи без разметки.
Одна семья сценариев не может входить в обе части. Не используйте ответы AI как эталон.

```powershell
.\.venv\Scripts\python.exe -m cqa.benchmark compare --labels tmp/manual-labels.json --split holdout --output tmp/comparison.json
```

Отчёт использует последнюю сохранённую AI-оценку для пары диалог/версия чек-листа:
совпадения по критериям, таблицу ошибок, precision/recall для N/A и грубых ошибок,
MAE итогового балла, пропущенные оценки и неподтверждённые записи. При отсутствии
разметки метрики равны null. Сохраняйте отдельные отчёты для сравнения экспериментов.
Это локальная проверка, не Ground Truth организаторов. Рост точности пока не измерен.

## Правила расчёта и обоснования

Версия инструкции `cqa-judge-v2` учитывает уточнение организаторов от 07.11.2026:
обоснованность важнее попыток угадать внутреннюю методику. Оценщик должен отмечать
нехватку данных в объяснении, не выдавать непроверенные тарифы и сроки за факты,
учитывать особенности устной речи и возможные ошибки STT. Это не меняет веса и
условия N/A. Старые результаты сохраняют свои исходные версии промпта и чек-листа.

```text
q(binary) = 1 для yes, 0 для no
q(scale) = score / max(scale)
total = round_half_up(100 * sum(weight * q) / sum(applicable_weight), 2)
```

- N/A исключается и из числителя, и из знаменателя.
- `flag` не участвует в расчёте; `yes` добавляет его в `flagged_criteria`.
- При нулевом знаменателе `total_score=null`.
- Промежуточные вычисления выполняются через Decimal. Округляется только итог.
- HALF_UP — текущая политика реализации, её подтверждение организаторами ещё ожидается.
- `earned_weight` — вклад до нормализации; `effective_weight` — вес после исключения N/A;
  `contribution` — вклад в нормализованный итог. Значения по критериям не округляются до сотых.
- Результат секции нормализован по применимым весам внутри этой секции; результаты секций не суммируются.
- Доказательства отображаются из оригинальных сообщений, а не из текста, сочинённого моделью.
- `checked_range` включительный, задаётся ID начала и конца.
- Политика `first_operator` требует ссылки на первый ответ оператора для положительной оценки.
  `operator` требует хотя бы одну реплику оператора; `any` допускает системные подтверждения.

Валидатор проверяет структуру, ссылки и некоторые правила ролей. Он **не доказывает**,
что выбранная цитата действительно подтверждает решение или что N/A семантически верен.
Это задача модели и последующей проверки на ручной разметке. Инструкция не является
гарантированной защитой от всех prompt injection; текст диалога передаётся как недоверенные данные.

## Проверки

```powershell
.\.venv\Scripts\python.exe -m pytest backend/tests -q
.\.venv\Scripts\python.exe -m ruff check backend
.\.venv\Scripts\python.exe -m ruff format backend --check
cd frontend
npm.cmd run build
```

Тесты не обращаются к внешним моделям и не тратят кредиты. Они проверяют арифметику,
N/A, шкалы, роли и доказательства, изменение чек-листа, сохранение снимков, API и
ошибки провайдера, обработку аудио, роли STT, дискретные ответы Jev и сохранность
основной оценки при расхождениях. Значение точности относительно Ground Truth ещё не измерялось.

| [Golos](https://huggingface.co/datasets/SberDevices/Golos) | Дополнительный русский STT, в том числе farfield | В HF — карточка и ссылки на внешние архивы; не готовый набор диалогов по нашему чек-листу |

Первый живой прогон: шесть полных расшифровок AppTek, по одной из banking,
finance, insurance, telecom, retail, travel. Выбраны первые имена файлов в каждой
сфере из `diarization/en-US_General`, до получения ответов модели. В запрос
передавался только текст с границами строк и язык EN, без ролей и таймкодов.
Разметка источника оставалась только у проверяющего скрипта. Данные не импортировались
в рабочую базу диалогов.

Результат: 638 из 651 строки с верной ролью (98,00%), четыре из шести разговоров
без ошибок ролей, исходный текст сохранён во всех шести. Это небольшой диагностический
прогон на английском, **не оценка точности чек-листа, STT или работы на RU/KZ**.
Метрики считаются по исходным строкам независимо от объединения реплик моделью.
Сохранены [ревизия источника, хеши, выборка и результаты](benchmarks/external-speakers-2026-11-07.json).

Обнаруженные проблемы: короткие междометия, повтор чисел и короткие встречные
вопросы могут получить неверную роль без отметки о сомнении. Для аудио следует
определять роль по совокупности реплик одного STT-говорящего, сохраняя его ID.
Флаг `needs_review` сам по себе не гарантирует обнаружения всех ошибок.

Второй прогон: ровно два примера из каждого из четырёх источников, шесть аудиофайлов
и два текстовых диалога. AppTek — два новых полных звонка (второе имя файла в banking
и insurance); FLEURS — первый файл с эталонным текстом в каждом из test-архивов RU/KZ;
KSC2 — первые две полные пары FLAC/TXT, встретившиеся в исходном Test/crowdsourced;
ABCD — первые два диалога авторского sample-файла. Отбор сделан до запросов модели.

| Набор | STT: WER на двух примерах | Верные роли по эталонному тексту |
| --- | --- | --- |
| FLEURS, RU и KZ | 0% / 0%, всего 42 слова | Не проверялись: одноголосное чтение |
| KSC2, KZ | 0% / 0%, всего 27 слов | Не проверялись: одноголосное чтение |
| AppTek, EN | 5,51% / 10,36% | 113/118 и 47/53 исходных строк |
| ABCD, EN | Текстовый набор | 28/29 и 19/21 исходных строк |

WER — доля вставок, пропусков и замен слов относительно эталона, меньше лучше.
Использована одинаковая нормализация эталона и гипотезы: Unicode NFKC, нижний регистр,
ё→е, удаление пунктуации; числа не переводятся в слова, междометия не удаляются.
Это не официальный протокол WER AppTek. Ноль ошибок на коротких фрагментах не означает
идеальное STT. Роли проверялись отдельно на эталонном тексте, не на результате STT.
[Результаты, происхождение и ограничения второго прогона](benchmarks/external-eight-samples-2026-11-07.json).
Все восемь примеров обработаны; аудио и подробные ответы находятся в отдельной
локальной базе `tmp/external-datasets/eight-samples/benchmark.sqlite3`, не в рабочем
списке диалогов. Сначала тестовая обвязка не инициализировала эту базу; ошибка возникла
до вызова STT-провайдера. После исправления все шесть аудиозаписей обработаны успешно.

Для качества оценивания нужен отдельный ручной набор с нашим чек-листом:
RU/KZ/EN, неполные записи, N/A, грубые ошибки и спорные консультации. Размечать
его следует независимо от ответов модели, разделяя сценарные семьи на настройку
и отложенную проверку. Существующий `cqa.benchmark` считает совпадения по критериям,
MAE итогового балла и precision/recall N/A и грубых ошибок. Новые внешние данные
не следует автоматически объявлять Ground Truth по нашим восьми критериям.

### Экспорт для организаторов · JSON 1.0

Раздел **«Сдача»** проверяет исходный набор и выгружает `results.json`.
Название команды — Bibigon; поле доступно для изменения.
DEV должен содержать 60 чатов и 5 звонков, PROD — ровно 10 чатов. Состав фиксируется
при импорте ответа API организаторов; фильтры интерфейса, добавленные вручную диалоги,
повторные расшифровки и QA-апелляции не подменяют исходный набор.

Используется последняя сохранённая AI-оценка **точного исходного транскрипта** и выбранной
версии чек-листа. Проверяются восемь критериев, веса, шкалы, N/A, ссылки и пересчитанный
итог. Несовместимая версия чек-листа блокирует экспорт. Внешние коды: `needs` →
`discovery`, `management` → `dialogue`, `closing` → `closure`. В `value` записывается
boolean/null/исходная ступень шкалы, не взвешенный вклад. `evidence_turns` — позиции
с 1 по всему исходному транскрипту, включая клиента, бота и события; проверенный
диапазон включается целиком. `critical_flag` не обнуляет балл. Отсутствующая или
невалидная оценка превращается в `status=error`, `criteria=[]`, `score=null` с причиной.
Файл с такими записями можно скачать после явного подтверждения.

Фактические названия моделей берутся из сохранённых оценок, включая исторические,
а не из текущей настройки. В этой версии оценщики используют внешние API, поэтому
`model.mode=external_api`. Если сведений о использованной модели нет совсем, экспорт
блокируется. Смена основной модели не переименовывает старые результаты. Значение
`ready` означает соответствие формату, а не отсутствие ошибок обработки.

CLI создаёт правильные папки и файл в UTF-8 без BOM; LLM не вызывает:

```powershell
.\.venv\Scripts\python.exe -m cqa.submission --dataset tmp/dev-dataset.json --split dev --team-name Bibigon --checklist-hash <хеш_версии> --check
.\.venv\Scripts\python.exe -m cqa.submission --dataset tmp/dev-dataset.json --split dev --team-name Bibigon --checklist-hash <хеш_версии> --include-errors
```

Хеш версии доступен в `/api/checklists` после авторизации; через интерфейс он не нужен.
`--check` не записывает results.json; исходный набор регистрируется в локальной базе.
`--include-errors` разрешает сохранить записи ошибок, `--overwrite` — явно заменить
существующий файл. Целевые пути: `results/dev/results.json` и `results/prod/results.json`.
Браузер скачивает файл; его нужно положить в показанную папку репозитория самостоятельно.
Commit/push автоматически не выполняются.

На 7 ноября 2026 выполнен полный новый DEV-прогон: 65 исходных ID, 65 записей `ok`,
0 записей `error`. Все оценки получены через `deepseek/deepseek-v4.1-flash-1017`,
инструкция `cqa-judge-v3-omnichannel`. Файл проверен против сохранённых результатов;
это успешная обработка, не измеренная точность относительно Ground Truth. PROD-файл не создаётся до получения контрольных данных.
Приложение требует два знака после округления, но не уточняет HALF_UP для ровной половины.
Сохранён текущий единый Decimal-расчёт с HALF_UP.

### Технические ограничения

Оценка пока выполняется в рамках HTTP-запроса. Очередь заданий, восстановление
незавершённой работы и пакетная оценка — следующий этап. При обрыве процесса журнал может
остаться в состоянии started; автоматического возобновления нет. Успешные результаты остаются в SQLite.
Кэш оценок пока отсутствует: каждый POST запускает модель заново.

До сравнения моделей нужен набор ручных оценок по критериям. В DEV-ответе
организаторов эталонных оценок нет. Похожие сценарии на разных языках следует
держать в одной группе при разделении на настройку и отложенную проверку.

Документация API провайдеров:
- [OpenRouter Structured Outputs](https://openrouter.ai/docs/guides/features/structured-outputs)
- [OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)
- [OpenRouter STT](https://openrouter.ai/docs/guides/overview/multimodal/stt)
- [OpenRouter Decisions](https://openrouter.ai/docs/api/api-reference/alphadecisions/submit-a-decisions-request)

Дизайн и происхождение фирменных материалов описаны в `DESIGN.md`, подтверждённые
продуктовые требования — в `PRODUCT.md`. Логотип и CoFo Sans взяты с официального
сайта `fbroker.kz`; отдельный публичный брендбук брокера не подтверждён.

### Автоматические участники аудио

После распознавания загруженного файла приложение определяет клиента и оператора
по совокупности реплик каждого STT-говорящего, затем создаёт диалог. Ручные списки
ролей из аудиоформ убраны. Для старых расшифровок доступна кнопка «Подготовить диалог».
Результат хранится отдельно с происхождением `confirmation_source=automatic`, моделью
и ссылками на реплики; исходный STT-текст не меняется. Открытие сохранённой записи не
вызывает модель, повторная подготовка готового диалога использует сохранённый результат.
Если участников недостаточно, STT не разделил речь или модель отметила сомнение,
расшифровка остаётся доступной, а диалог для оценки автоматически не создаётся.
Ошибка определения ролей позволяет повторить этот шаг без повторного STT.

### Оценка вставленного текста одним действием

В форме вставки текста остались необязательное название, текст и кнопка «Оценить диалог».
После нажатия клиент вызывает разбор в фоне, сохраняет исходные реплики и запускает
оценку по последней версии стандартного чек-листа. Затем открывается обычная карточка:
переписка слева, оценка с обоснованиями справа. Промежуточный редактор реплик и ролей
удалён. Если оценка завершилась ошибкой, повторная попытка использует сохранённый
диалог; если не удалось обновить экран после успешной оценки, оплаченный результат
повторно не запрашивается. При изменении текста/названия начинается новая попытка.
Живой интеграционный пример «Проверка комиссии · один шаг» обработан DeepSeek;
полученные 45,5 балла — вывод модели, не экспертный Ground Truth.
